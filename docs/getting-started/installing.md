# Installing patchy

patchy installs onto an existing cluster from any root that can read the cluster root's `application_target` output.
That's usually a root of its own, in another state. The cluster root isn't touched: it has no `applications`,
`application_vars`, `workload_grants`, `secret_readers` or `flux.namespaces` entry for patchy, and needs none.

## The module call

=== "aws"

    ```hcl
    data "terraform_remote_state" "cluster" {
      backend = "s3"
      config  = { bucket = "...", key = "clusters/patchy-x.tfstate", region = "eu-west-2" }
    }

    module "patchy" {
      source = "git::https://github.com/bitwise-media-group/patchy-app-manifests.git//modules/aws?ref=vX.Y.Z"

      cluster     = data.terraform_remote_state.cluster.outputs.application_target
      domain      = "patchy.example.com" # the cluster's served host: dex lives at dex.<host>
      harnesses   = ["claude"]
      claude      = { provider = "anthropic" }
      sso_enabled = true # the cluster elects dex
      evaluation  = { enabled = false }
    }
    ```

    The root needs an `aws` provider in the cluster's account and region, and a `helm` provider pointed at the cluster.

=== "google"

    ```hcl
    module "patchy" {
      source = "git::https://github.com/bitwise-media-group/patchy-app-manifests.git//modules/google?ref=vX.Y.Z"

      cluster     = data.terraform_remote_state.cluster.outputs.application_target
      domain      = "patchy.example.com" # the cluster's served host: dex lives at dex.<host>
      harnesses   = ["claude"]
      claude      = { provider = "vertex" } # or "anthropic"
      sso_enabled = true # the cluster elects dex
      evaluation  = { enabled = false }
    }
    ```

    `cluster` is terraform-google-gke-flux's `application_target`. The root needs a `google` provider in the cluster's
    project, and a `helm` provider pointed at the cluster.

Each module calls its cluster repository's `modules/application`, which is why the root needs that module's providers.

## What each module creates

| What                      | aws (`modules/aws`)                                                           | google (`modules/google`)                                    |
| ------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------ |
| seed                      | `application-patchy` release: the RSIP + ResourceSet `patchy-manifests`       | same                                                         |
| `patchy-vars`, namespaces | `application-patchy-inputs` release: the ConfigMap, `patchy`, `patchy-agents` | same                                                         |
| credential containers     | Secrets Manager, `<SECRET_PREFIX><name>`                                      | Secret Manager in `cluster.project`, `<SECRET_PREFIX><name>` |
| secret reads              | IRSA reader roles `<cluster>-secrets-<ns>-patchy-secrets`                     | `secretAccessor` per container for the sync KSA's principal  |
| egress-broker model grant | `<cluster>-patchy-egress-broker` (Pod Identity), under `bedrock`              | `aiplatform.user` for the broker's principal, under `vertex` |

The image URL (`oci://<platform_registry>/manifests/patchy`), the secret prefix and the signing mode all come from
`application_target`. On a keyless cluster the seed verifies the image against `signed_identity_subject`; on a KMS-keyed
one, against the `cosign-pub` Secret.

## Inputs and outputs

**Inputs:** `cluster`, `domain`, `harnesses`, `claude`, `evaluation`, `sso_enabled`, `egress_policy`,
`manifests_semver`, `signed_identity_subject`, `extra_vars`, and `tags` (aws) or `labels` (google).

**Outputs:** `release`, `vars`, `secrets`, and `workload_roles` + `secret_reader_roles` (aws) or `workload_members`
(google).

The full tables, generated by terraform-docs, are on the [aws](../reference/modules/aws.md) and
[google](../reference/modules/google.md) module pages.

- **Credential versions are added out of band.** The modules create the containers only; the versions are destroyed with
  the module.
- **`sso_enabled` declares no secrets.** It adds the platform's `dex` Kustomization to the seed's `dependsOn` (the
  image's own Kustomization does the same once it owns itself), and `evaluation` requires it.

## Security Command Center findings

On google, Security Command Center findings reach patchy through
[`modules/scc-notifications`](../reference/modules/scc-notifications.md), a standalone module: a topic, a notification
config, an OIDC-authenticated push subscription and a dead-letter queue. Apply it on its own after the cluster, with an
identity that holds `roles/securitycenter.admin` at the organization. Its pipeline values reach the manifests through
`extra_vars`.

## One root only

!!! warning "patchy lives in exactly one root"

    `modules/application` mints the same names a cluster root would for an application it seeds itself, so a second
    copy (or a leftover `applications.patchy` in the cluster root) fails loudly on the helm releases and, on aws, the
    IAM roles. On google an IAM member binding is shared rather than owned, so destroying one copy would also remove
    the other's grant.

Coming from a cluster root that still carries patchy? See
[Moving out of the cluster root](../upgrading/cluster-root.md).
